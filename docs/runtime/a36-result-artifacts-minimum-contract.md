# A36 — минимальный контракт артефактов результата URI

## Назначение

Этот документ фиксирует **минимальный эксплуатационный контракт артефактов результата** для `uri-runner-next`.

Цель документа:
- сделать поведение раннера предсказуемым для Макса и Алекса;
- отделить **обязательный минимум** от расширенных диагностик;
- зафиксировать, что даже при ошибке раннер обязан возвращать минимально пригодный результат;
- дать опорный критерий для watcher / outbox / pipeline изменений.

Документ опирается на уже подтверждённое состояние проекта:
- полный цикл `preflight → classification_required → classification-response → rerun → execute`;
- real/truth coverage через watcher pipeline;
- `test/real/scenario.profile.real.test.mjs` как canonical truth gate для scenario;
- требование подтверждать browser runtime изменения через real watcher pipeline, а не только unit-тестами.

## Базовый принцип

URI — это **контролируемый runner**, а не слепой shell-proxy.

Поэтому после любого запуска должен существовать **результат выполнения**, пригодный для дальнейшей автоматической обработки.

Это означает:
- успешный запуск обязан давать success-result;
- неуспешный запуск обязан давать failure-result;
- `classification_required` не должен разрушать контракт результата;
- отсутствие минимального outbox/result-пакета считается эксплуатационной регрессией.

## Минимальный результат обязателен всегда

После любого завершённого запуска должен существовать **минимальный набор артефактов результата**.

Минимум:
1. отдельный `outbox`-контейнер результата;
2. машиночитаемый result payload;
3. явный итоговый статус запуска;
4. достаточный минимум метаданных, чтобы понять:
   - что было запущено;
   - чем закончился запуск;
   - где искать дополнительные артефакты, если они есть.

## Минимальный контракт outbox

Минимальный outbox-контракт:
- должен существовать **проектный outbox / project-owned результат**;
- результат должен быть пригоден для чтения следующим шагом pipeline;
- success и failure режимы должны иметь **одинаковую базовую оболочку**, даже если содержимое отличается;
- если есть zip-формат результата, он должен собираться и в success, и в failure ветке.

### Что считается обязательным

Обязательным считается наличие:
- итогового result payload;
- итогового статуса;
- привязки результата к конкретному запуску/попытке;
- возможности отличить success, failure и classification-related outcome.

### Что считается желательным, но не обязательным минимумом

Желательно, но не входит в минимальный контракт:
- расширенные логи;
- подробные browser diagnostics;
- промежуточные trace-артефакты;
- дополнительные summary-файлы;
- debug dump-и.

Если они отсутствуют, это ещё не нарушение минимального контракта.

## Минимальный контракт result payload

Result payload должен содержать минимум следующие логические поля.

### 1. Идентификация запуска
Должно быть возможно определить:
- какой запуск породил результат;
- к какому сценарию / инструкции / пакету он относится.

Минимально допустимо:
- `runId` или эквивалентный идентификатор;
- `source` / `input` / `scenario` / `request`-ссылка любого устойчивого типа.

### 2. Итоговый статус
Должно быть явное поле статуса.

Минимально допустимые смысловые категории:
- `success`;
- `failure`;
- `classification_required` или эквивалентный классификационный блокирующий статус.

Главное требование:
**статус должен быть определим без чтения логов.**

### 3. Краткое объяснение результата
Должно быть короткое человеко- и машиночитаемое объяснение:
- что произошло;
- почему запуск завершился так, а не иначе.

Минимально допустимо:
- `message`;
- `summary`;
- `reason`;
- или эквивалентное поле.

### 4. Ссылка на полезные артефакты
Если запуск породил дополнительные материалы, payload должен позволять понять, где они лежат.

Минимально допустимо:
- список артефактов;
- список путей;
- карта outputs;
- или эквивалентная структура.

Если дополнительных артефактов нет, это допустимо, но payload всё равно обязан существовать.

## Контракт по режимам завершения

### Success
В success-ветке обязаны выполняться все минимальные условия:
- существует result payload;
- статус отражает успех;
- есть краткое summary;
- есть ссылка на дополнительные результаты, если они были созданы.

### Failure
В failure-ветке также обязаны выполняться все минимальные условия:
- существует result payload;
- статус отражает failure;
- есть краткая причина ошибки;
- outbox/result остаётся валидным и пригодным для чтения;
- failure не отменяет сборку минимального результата.

### Classification required
`classification_required` считается **валидным контролируемым исходом**, а не поломкой пайплайна.

Значит:
- result payload обязан существовать;
- статус должен явно указывать на необходимость классификации;
- в результате должно быть понятно, что именно нужно классифицировать или подтверждать;
- дальнейший rerun после classification-response не должен требовать изменения базового контракта результата.

## Что считается блокирующей регрессией

Ниже перечислены изменения, после которых URI нельзя считать готовым к работе.

### Блокирующие регрессии
1. После запуска не появляется минимальный result payload.
2. В failure-ветке outbox/result отсутствует или нечитаем.
3. Статус результата можно понять только по логам, но не по payload.
4. `classification_required` ломает общий результатный контракт.
5. Success и failure ветки требуют принципиально разного парсинга без общей базовой оболочки.
6. Browser/runtime или watcher-изменение ломает сборку минимального результата.
7. Изменение проходит unit-слой, но ломает real watcher pipeline.

## Минимальные проверки после чувствительных изменений

После изменений в watcher / outbox / scenario runtime / browser runtime / policy рекомендуется минимум:

1. прогон canonical scenario truth gate;
2. проверка, что success-case создаёт валидный result;
3. проверка, что classification-case создаёт валидный result;
4. проверка, что failure-case не уничтожает минимальный outbox/result контракт;
5. для browser runtime — подтверждение через real watcher pipeline.

## Practical done-критерий

Минимальный контракт артефактов результата считается внедрённым, когда одновременно верно следующее:

1. В docs/runtime явно зафиксирован этот минимум.
2. Success / failure / classification outcomes имеют общую базовую result-оболочку.
3. Изменения в watcher/runtime проверяются не только unit-слоем, но и real pipeline там, где это требуется.
4. Отсутствие минимального outbox/result считается официальной блокирующей регрессией.

## Короткая каноническая формулировка

> URI обязан возвращать минимально пригодный результат после каждого завершённого запуска.
> Даже при failure или classification_required должен существовать читаемый project-owned outbox/result payload
> с явным статусом, кратким объяснением и возможностью связать результат с конкретным запуском.
> Отсутствие такого результата считается блокирующей эксплуатационной регрессией.
