# docs/runtime/command-registry-spec.md

## Назначение

`command-registry` — канонический реестр известных команд URI для режима разработки.

Реестр нужен, чтобы:
- до выполнения сценария определить, известны ли все команды;
- привязать известную команду к группе разработки и runtime-профилю;
- убрать угадывание во время исполнения;
- сделать truth-tests системными: сценарий либо исполняется по известным правилам, либо корректно уходит в `classification_required`.

## Базовый принцип

URI не должен исполнять неизвестную команду.

Правильный цикл такой:
1. получить сценарий;
2. сделать `preflight`;
3. если все команды известны — выполнить сценарий;
4. если есть неизвестные — не выполнять сценарий, а сформировать `classification-request`;
5. после `classification-response` обновить реестр;
6. повторить `preflight`;
7. выполнить сценарий.

## Область применения

Реестр описывает только команды, необходимые для разработки.

Стартовый MVP-фокус:
- `inspect`
- `test`
- `server`
- `db-query`
- `browser`

Позже можно добавить:
- `migration`
- `build`
- `lint`
- `git-write`
- `cleanup`

## Структура реестра

Файл: `config/command-registry.yaml`

Верхний уровень:
- `version` — версия схемы реестра;
- `profiles` — словарь runtime-профилей;
- `commands` — список matcher-правил;
- `defaults` — поведение для команд, не найденных в реестре.

## Runtime-профили

Минимальный набор MVP:

### `instant`
Для команд, которые должны завершаться быстро и самостоятельно.

Ожидания:
- процесс завершается сам;
- не нужен readiness-check;
- exit code обязателен;
- stdout/stderr могут присутствовать.

Примеры:
- `pwd`
- `ls`
- `git status --short`
- `psql -c "select 1"`

### `short_wait`
Для команд, которым нужно небольшое время, но которые тоже должны завершиться сами.

Ожидания:
- процесс завершается сам;
- timeout больше, чем у `instant`;
- readiness-check не нужен.

Примеры:
- `npm test`
- короткий `vitest run`

### `readiness`
Для команд, которые поднимают сервис и не должны завершаться сразу.

Ожидания:
- процесс продолжает жить;
- нужна проверка готовности;
- успех определяется не по exit code, а по достижению состояния ready;
- после готовности процесс должен корректно останавливаться runtime-ом.

Примеры:
- `npm run dev`
- `node src/server.js`

### `browser_scenario`
Для browser-команд и сценариев, где исполнение идёт через браузерный executor.

Ожидания:
- шаги сценария могут включать open/wait/diagnostics;
- критерии успеха определяются по browser-artifacts и runtime-report.

## Dev-группы

Каждая команда в реестре должна иметь `group`.

Минимальные значения:
- `inspect`
- `test`
- `server`
- `db-query`
- `browser`

Группа нужна для:
- понятной карты возможностей URI;
- построения truth-матрицы по группам;
- будущих policy-ограничений.

## Matcher-логика

Правило в `commands` описывает семейство команд, а не обязательно одну точную строку.

Минимально поддерживаемые matcher-поля:
- `cmd` — имя бинарника или базовой команды;
- `args_prefix` — префикс аргументов;
- `args_exact` — полное точное совпадение аргументов;
- `args_contains` — список аргументов, наличие которых обязательно.

Приоритет matcher-ов:
1. более специфичный matcher;
2. более длинный `args_prefix`;
3. более ранняя запись в реестре.

## Defaults

Если команда не найдена в реестре:
- сценарий не выполняется;
- статус `preflight` становится `classification_required`;
- формируется `classification-request`.

То есть default-поведение — не исполнение, а остановка до классификации.

## Обязательные поля записи команды

Каждая запись `commands[]` должна содержать:
- `id`
- `group`
- `profile`
- `match`
- `notes`

Рекомендуемые поля:
- `timeouts`
- `readiness`
- `risk`
- `examples`

## Требования к стабильности реестра

1. Реестр — канонический.
2. URI не должен самопроизвольно переписывать канонический реестр в runtime.
3. Изменение реестра происходит только через явный `classification-response`.
4. Неизвестные команды не должны исполняться до обновления реестра.

## Truth-ориентация

Для MVP truth-test должен проверять полный цикл:
- известный сценарий -> `preflight: ready_to_execute` -> execution -> outbox;
- сценарий с неизвестной командой -> `preflight: classification_required` -> `classification-request`;
- после ответа -> обновление реестра -> `preflight: ready_to_execute` -> execution.
