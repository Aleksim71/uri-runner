# URI Runtime Contract (A33)

## Назначение
URI — это контролируемый runner для выполнения инструкций проекта через формализованный runtime-cycle.
URI не считается «слепым shell-прокси для любых команд». Базовая модель — это проверяемое и классифицируемое исполнение с предсказуемыми артефактами результата.

## Каноническая модель
Базовый контракт работы URI:

**Max / оператор → inbox / instruction package → preflight → classification (если нужно) → execute → outbox / result artifacts**

Для scenario/runtime слоя canonical execution cycle:

**preflight → classification_required → classification-response → rerun → execute**

Если классификация не требуется, цикл может перейти из `preflight` сразу в `execute`.

## Что URI принимает
URI принимает структурированные инструкции проекта, упакованные в согласованный входной формат runner-а.
На уровне эксплуатационного контракта это означает:
- входной пакет должен быть пригоден для preflight-проверки;
- инструкции должны быть интерпретируемы как разрешённые runtime-операции;
- неизвестные, неоднозначные или неразрешённые действия не должны исполняться вслепую.

## Что делает preflight
Preflight обязан:
- проверить, что вход валиден для runtime;
- определить, какие действия можно исполнять сразу;
- определить, какие действия требуют classification;
- не допускать blind execution для неясных / неизвестных операций.

## Когда возникает classification_required
Статус `classification_required` возникает, если runner не может безопасно и однозначно исполнить часть инструкций в текущем виде.
Типовые причины:
- неизвестная named command;
- неизвестное browser action;
- операция не имеет достаточного разрешения / описания в текущем runtime-контуре.

В этом состоянии URI не должен имитировать успешное выполнение. Он обязан вернуть управляемый результат, из которого понятно, что требуется classification-response.

## Что делает classification-response
`classification-response` уточняет или разрешает ранее неисполняемую часть входа.
После применения classification-response runner обязан повторно пройти preflight (`rerun preflight`) и только затем перейти к execute.

## Что считается допустимым исполнением
Допустимое исполнение URI — это только то исполнение, которое:
- прошло preflight;
- не нарушает classification / registry / policy-контур;
- приводит к формированию предсказуемого набора result artifacts.

Иными словами, URI исполняет не «любые команды вообще», а только команды/шаги, допущенные текущим runtime-контрактом.

## Что URI возвращает
Результат работы URI должен оформляться как артефакты выполнения (`outbox`, result payload, сопутствующие runtime artifacts).
Эксплуатационно это означает:
- после run должен существовать читаемый результат;
- результат должен отделять success path от failure path;
- даже при ошибке должен существовать минимальный валидный результат runner-а, а не «тишина».

## Отдельная папка результатов
Канонический практический режим: URI складывает результаты выполнения в выделенную project-owned / outbox-папку проекта.
Это считается правильной моделью интеграции runner-а с рабочим проектом:
- вход приходит в согласованную intake/inbox-точку;
- результат уходит в согласованную processed/outbox-точку;
- артефакты не смешиваются с произвольным шумом рабочего дерева.

## Что считается ошибкой / блокером
Блокирующими считаются ситуации, в которых:
- runner обходит classification и пытается исполнить неизвестное действие;
- browser/runtime состояние ломается без управляемого result path;
- нет обязательных result artifacts;
- real / truth tests показывают regression в canonical flow.

## Source of truth
Для scenario-слоя source of truth должен опираться не только на unit/helper tests, но и на canonical real / truth coverage.
Для browser runtime одного unit-слоя недостаточно: изменения должны подтверждаться через real watcher pipeline.

## Операционное чтение контракта
В краткой форме URI следует понимать так:

> URI принимает структурированные инструкции проекта, прогоняет их через preflight и classification-контур, исполняет только допустимые шаги и возвращает предсказуемые артефакты результата в project-owned outbox.

## Минимальное правило для Max ↔ URI
Короткая формула взаимодействия:

**Max формирует задачу → URI проверяет и классифицирует → URI исполняет разрешённое → URI кладёт результат в отдельную папку артефактов.**

Это и есть базовый канонический runtime-контракт URI на текущем этапе проекта.

## Контракт Terminal UI для watch-вывода

### Область действия

Теперь watch-вывод поддерживает два режима отображения:

1. **Интерактивный терминал**
- человеко-ориентированный themed output
- выбор темы: `dark`, `light`, `auto`
- выбор пресета палитры
- опциональное переопределение цветов через конфиг

2. **Неинтерактивный режим**
- legacy plain-text stdout contract
- обязателен для тестов, CI и других non-TTY потребителей

### Конфиг

Файл конфигурации terminal UI:

- `config/terminal-ui.json`

### Переменные окружения

Поддерживаются следующие override-переменные:

- `URI_TERM_THEME`
- `URI_TERM_PRESET`
- `URI_NO_COLOR`

### Правило рендеринга

- interactive TTY → themed UI layer
- non-TTY / tests / CI → legacy plain-text output

### Требование совместимости

Любые будущие улучшения terminal UX не должны ломать legacy stdout-контракт для неинтерактивного режима, который используется real-тестами и автоматизацией.
